# 05: Hide locked private apps from favorites

**What to build:** While Private Space is **locked**, private apps disappear from favorites, along with any pop-up attached to them. When the user unlocks, they come back in their old positions. Locking, unlocking and rebooting never remove a **placement**.

**Blocked by:** 01: Add a private app to favorites from its long-press menu

**Status:** done-pending-device-check

- [x] **Locked detection:** based on "is Private Space" plus Android's quiet-mode state for the private user, or Niagara's locked flag. Never Niagara's "hidden everywhere" state, which is also true for suspended apps while unlocked. Unit tests cover a suspended private app staying visible while unlocked.
- [x] **Decision module:** decides which rendered favorites rows to keep. Unit-tested for: locked private hidden; unlocked private shown; personal and work never hidden.
- [ ] **Rendering only:** the hook filters only the rows being rendered, never the stored favorites list. After locking, editing favorites and unlocking, every private placement is still there.
- [ ] **Updates:** favorites update on lock and unlock without restarting Niagara.
- [x] **Hook is essential:** it's added to the essential set.
- [ ] **On the phone:** the user locks Private Space for a while, reboots, and unlocks. Every placement survives, confirmed by reading Niagara's database as root. Done only with the user's go-ahead.
- [x] **Device check:** steps added.

## Notes

- **Locked detection** is `PrivateSpaceState.isLocked()`: Android's quiet mode for the profile whose `LauncherUserInfo` type is `android.os.usertype.profile.PRIVATE`, asked when the row is built, only for items Niagara marks as private. It is never Niagara's "hidden everywhere" state. Any failure (no private profile found, an exception) counts as locked: wrongly hiding an app is noticed at once, wrongly showing one is not.
- **The decision is `Decisions.mayBeListed(kind, locked)`**, the same rule ticket 04 wrote for suggestions: personal and work apps always, a private app only while Private Space is unlocked. It takes nothing but the profile and the lock state, which is how "a suspended private app stays visible while unlocked" holds. The three ticket tests (locked hidden, unlocked shown, suspended still shown) are in `ListingTest`; the last one restates the unlocked case in the ticket's words and says why, since there is no input for "suspended" to vary.
- **Why it is called by every home page section, not just favorites.** Three sections turn a placed item into a row (favorites, most-used suggestions, media). Ticket 03 lets private apps into the music-apps picker, ticket 04 lets them into suggestions; both would otherwise show a locked private app. So the hook sits on all three row providers: `FAVORITES_ROWS` (found by its log string `requestHsi: %s index: %s`) and `OTHER_HOME_ROWS` (the sibling providers, found by signature and by extending the favorites section's base class, at any depth; two on 1.16.32: suggestions and media). Both queries were emulated over the 1638 dexdump, not run in DexKit. Both are essential. The media section was not in the spec's list; see "Home page sections" in the research notes.
- **Rendering only, and Updates (left unchecked on purpose).** The hook is an after-hook on the row providers: it lets Niagara build the row, then answers null for a locked private app. The stored feeds are never touched. In the 1638 bytecode exactly one method, `MOctxdZAQ6hZ.pTm4A75…`, asks the providers, and it passes a null row back to both the full build and the incremental update, which skip it. Locking swaps in new item instances, so the rows should be asked for again and the page should update without a restart. Both are read from the code, and both criteria end in a phone outcome (placements survive editing while locked; the page updates), so they stay unchecked until the device check has run.
- **Known leak, outside this ticket's text and not fixed: the favorites and folder editors list the current selection, locked private apps included.** They draw it from the stored feed without a lock check, and removing private apps from the selection would delete the placements on save. A hook on the editor's row-adding step might fix it without touching the selection; see "Home page sections" in the research notes. Left for a later ticket.
- **Limits of the tests.** "A suspended private app keeps its row while unlocked" cannot fail by construction, because `mayBeListed` has no suspended input; the comment in `ListingTest` records the reason. With favorites hidden, the suggestion section's eight-row cap frees up, so other suggestions can appear while locked.
- **Folders and pop-ups are not covered here** (ticket 07); a pop-up attached to a private favorite is hidden with its row.
- **Timing of the lock state (AOSP, unchecked on LineageOS 24).** Niagara rebuilds the rows in response to `PROFILE_UNAVAILABLE` and `PROFILE_AVAILABLE`. Android's `UserManagerService` sets or clears the profile's quiet-mode flag before it sends those broadcasts, so `isQuietModeEnabled` should already show the new state when the rows are asked for. If it did not, the page would show the old state until the next rebuild; the device check's lock and unlock steps would show it.
- **Unverified on the phone:** every step of the new device-check section, in particular that `getActivityList` keeps returning the private apps while locked (no 256 or 512 bit), which the spec says was verified on 2026-10-17 (for a short lock; a lock of days has not been tried).
