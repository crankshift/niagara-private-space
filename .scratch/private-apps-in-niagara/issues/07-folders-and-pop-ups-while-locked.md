# 07: Folders and pop-ups while locked

**What to build:** While Private Space is locked, folders and pop-ups stay visible. Their private apps are hidden, and a row reads "Unlock Private Space to see your apps", below any personal or work apps. Tapping that row brings up Android's unlock screen, and the private apps appear once the user unlocks. If a Niagara version breaks the borrowed message row, private apps are hidden with no message, and the rest of the module keeps working.

**Blocked by:** 05: Hide locked private apps from favorites; 06: Tapping a locked private app unlocks it, then opens it

**Status:** done-pending-device-check

- [x] **Decision module:** decides the rows of a folder or pop-up and whether to add the unlock message, with and without the message row available. Unit tests cover:
  - a folder of only private apps;
  - a mixed folder;
  - an unlocked folder;
  - a folder with no private apps.
- [x] **Rendering only:** the hook filters the rows built by the shared folder and pop-up list controller, never the stored contents.
- [x] **Message row:** a borrowed instance of Niagara's empty-pop-up row, with its text and tap replaced. Tapping it uses the unlock request from ticket 06.
- [x] **Hook classes:** the row filter is **essential**. The message row is **optional**: when it's missing, the decision module falls back to hiding without a message, and the activation log line records it.
- [ ] **On the phone:** the user's hand-made folders (e.g. "Ciklum") show the unlock message while locked and their private apps after unlocking from it. Whether the folder or pop-up stays open behind the unlock screen is verified and recorded.
- [x] **Device check:** steps added.

## Notes

- **Decision shape.** `Decisions.folderOrPopUpContents(rows, kindOf, privateSpaceLocked, unlockMessageRowAvailable)` returns `FolderContents(rows, showUnlockMessage)`. It is generic over the row type, so the tests use plain apps with a profile kind and the adapter passes Niagara's rows with a lookup. It keeps the rows that `mayBeListed` (the rule tickets 04 and 05 use), in order, and asks for the message only when a row left and a message row exists. `FolderContentsTest` has the ticket's four cases (folder of only private apps, mixed folder, unlocked folder, folder with no private apps) plus an empty folder and the missing message row.
- **The essential/optional split arrives here, as planned.** `Hook` now carries an optional `OptionalPart`; a hook with none is essential. `OptionalPart.UNLOCK_MESSAGE_ROW` has six hooks (`EMPTY_POP_UP_ROW`, `EMPTY_POP_UP_ROW_BIND`, `EMPTY_POP_UP_ROW_CLICK`, `EMPTY_POP_UP_ROW_TEXT`, `POP_UP_HOST`, `POP_UP_NOTIFICATIONS`). `Activation.active` is true when no essential hook is missing, `availableParts` holds the parts none of whose hooks is missing (empty while inactive), and the log line of an active module ends `; without UNLOCK_MESSAGE_ROW (missing: …)` when one is lost. `ActivationTest` covers: every essential hook, each optional hook missing keeps the module active, a part is available only when all its hooks were found, no part when inactive, and the log line both ways. `TIP_SYSTEM`, the spec's other optional part, arrives with ticket 08.
- **All of an optional part or none of it.** In the finder the whole message row is one `attempt`: if any piece fails to resolve, none of its six hooks are reported, so the part is missing. In the installer, setting up the row from the resolved pieces and installing its two hooks is guarded too (`InstalledHooks.optional`): if anything throws, the hooks the part added are removed, the part is dropped with a warning, the rest installs, and the activation log line ends `; UNLOCK_MESSAGE_ROW left out at install`.
- **Rows are filtered, never the stored contents.** `FolderHooks` is an after-hook on the row builder `gcZiy9TwlTwZ.myg4xWl4jc7ydenlyX4YW()`. It lets Niagara build the rows, reads each row's app from the app row class's field (`FOLDER_AND_POP_UP_ROW_ITEM`), asks `PrivateSpaceState.isLocked()` only if some row is a private app, asks the decision module, and returns the same list when nothing changed or a new list with the message appended. A pop-up attached to a private favorite is hidden with the favorite (ticket 05), so only a visible app's pop-up needs this.
- **The unlock message.** `UnlockMessageRow` builds Niagara's empty-pop-up row with the controller's host and notifications and remembers it by identity (all empty-state rows share one id and compare equal). Its bind hook sets the text "Unlock Private Space to see your apps" and skips Niagara's bind for our instance; its click hook sends the unlock request and skips Niagara's click. Niagara's own empty-pop-up rows are other instances and run as before. The message is English only; the module has no resources Niagara could read. Tapping the message calls `LaunchHooks.requestUnlockWithoutApp`, which first forgets an app an earlier tap left pending, so unlocking from a folder cannot open an app by surprise.
- **Long-press on the message** is left to Niagara: its row for an empty pop-up opens the pop-up editor for the host. That editor lists the stored contents, private apps included (the known leak, closed by the follow-up below).
- **Fingerprints checked on the 1638 dexdump** by emulating the finder's queries (a throwaway script, not DexKit): one class holds `"Popups can only be shown inside PopupDialogHosts"`, and it has one no-argument method returning `ArrayList`; one class holds `"Iihsi(i="`, the builder constructs two subclasses of it, and it has one field typed as the item base; two constructors use 412316860418, and only one has two parameters with the item base first; that class has one one-parameter void method (bind), one void method with `View` last of three parameters (click), and its bind reads one `TextView` field; the builder reads one field of the notifications type, and the one `final` field of the item type that it reads is the host.
- **What the host field rests on.** The controller has two fields of the item type that the builder reads: the host (`mGe4G6…`, `final`) and the app currently selected (`cHj5w…`, not final). The finder takes the one `final` one and requires exactly one, checked in the 1638 dexdump. (A first version relied on the order the builder reads them in; the review preferred the modifier.) If a Niagara update makes both final or neither, the host is missing and so is the message row, not the module.
- **Hook counts.** The log line gains `FOLDER_AND_POP_UP_ROWS`, `FOLDER_AND_POP_UP_ROW_ITEM` and the six borrowed-row entries; 16 hooks were installed after this ticket (14 without the message row), and 17 (15) after the follow-up below: `docs/device-check.md` has it.
- **Unverified on the phone** (criterion left unchecked): that the message row renders and its tap reaches our hook; whether the pop-up stays open behind the unlock screen; that after unlocking the folder shows its apps without reopening (inferred from the feed swap that Niagara does when the lock flag changes).
- **Review round.** /code-review found, and this commit fixes: building the message could throw and, with Niagara's protective mode, hand back the unfiltered rows (it is now guarded: the rows are still filtered, the message is left out, a warning is logged); installing the message row's two hooks was outside the guard that makes it optional (now `InstalledHooks.optional` removes whatever the part added and drops the part); the activation line did not say when the part was dropped at install (it does now); the host field rested on read order (now the one final field); the pop-up row hooks were named `MESSAGE_ROW…`, easy to mistake for the unlock message (now `EMPTY_POP_UP_ROW…`; `Host` joins the glossary); stale text in `Decisions.activation`, the "Pending app" glossary entry and two pointers to a "known leak" section that was elsewhere; a duplicate `UnlockMessageRow` class name in the finder; and a missing test for a folder of only private apps without the message row. Declined: moving "nothing changed" and the lock query into the decision module (the lock query is the adapter's job, and "nothing changed" is a size comparison of the decision's own answer); a unit test for `unlockCancelled` through the unlock message (it is the same behaviour as a failed request).
- **No code refreshes an open folder after unlocking.** Story 26 ("the folder shows its private apps as soon as I've unlocked from that message") rests on Niagara swapping new item instances into the host's feed when the lock flag changes (inferred, see the research notes) and reloading the pop-up from that; nothing in the module forces it. If the folder does not refresh, the user reopens it, and the device check (step 5) records it.
- **Follow-up: the known leak from ticket 05 (current selection of the pickers), tried and kept.** The favorites and folder editors, and every other picker, list the apps already chosen straight from Niagara's stored lists. A hook on the one static step that adds an app's row to a picker's list (`HdxOm26AKWF.HdbD73X0ZC0vBBjEb96BB` on 1638, `PICKER_ROW`, essential) skips the row for a locked private app (`PickerHooks.installRows`, asking `Decisions.mayBeListed`). **The chosen list is untouched, checked in the 1638 dexdump:** the step's only access to it is one `ArrayList.contains` (to mark a row as selected); it makes no write and calls no mutator. Reordering (`HdxOm26AKWF.ZPvKxZwSSD2N`) moves items inside the chosen list by their own index, and the pickers save that list, so hidden placements stay where they are. **Found by structure:** the one static void method of the picker base class (the class of the base picker filter) whose first parameter is that class and third is the item base; on 1638 it is the only one, and its three callers are the generic list builder, the widget-capable picker base and the pop-up editor. **Not shown on the phone:** that the hidden rows really disappear from every editor (the device check, "Edit while locked" in the home page section, asks), and that the row counts in section headers stay sensible. A header that counts the chosen apps may still count the hidden ones; that is cosmetic and nothing checks it.
- **Follow-up review round.** The picker row step is **essential**, which the spec's list of essential hooks did not foresee; the spec's Activation rule now names it (a locked private app's name in an editor is the kind of leak the essential set exists to stop). It targets a static method with Kotlin default arguments, which a Niagara update could inline, in which case the module goes inactive and the user is told. **Two limits, found in review and recorded in the device check:** (1) reordering in an editor (`HdxOm26AKWF.ZPvKxZwSSD2N`, which rotates the whole chosen list by index) and its "sort" action work on the whole stored list, hidden placements included. Nothing is deleted, but dragging an app across a hidden favorite, or sorting, can move that hidden favorite by a position, so story 21 ("hidden private favorites come back in their old positions") holds only if the user did not reorder while locked; (2) the step adds widget rows too, so the widget of a locked private app is hidden from the editor as well, which is wanted. The checked claim stays narrow: the step reads the chosen list and never writes it, for the pickers derived from `HdxOm26AKWF` (all eight, per the research); the pop-up editor's host row carries the host's own profile and is unaffected unless the host is private.
