# 04: Private apps in suggestions and app shortcuts

**What to build:** Private apps can appear in Niagara's suggestions below favorites, and their long-press menu offers "Stop suggesting" and "Suggest again". A private app's app shortcuts (e.g. "New chat") can be pinned to favorites or to the app list, and the "Add shortcut" screen lists private apps. While Private Space is locked, private apps stay out of suggestions, as Niagara already does.

**Blocked by:** 01: Add a private app to favorites from its long-press menu

**Status:** done-pending-device-check

- [x] **Decision module:** answers whether an item may be suggested and whether its app shortcuts may be pinned, with private apps treated like work apps. Unit-tested.
- [x] **Finder:** resolves the most-used suggestions check, the private-shortcut pin check and the "Add shortcut" screen check.
- [x] **Hooks are essential:** they're added to the essential set.

## Notes

- **Decision shape.** `Decisions.mayBeListed(kind, privateSpaceLocked)` is the rule behind "may be suggested": personal and work apps always, a private app only while Private Space is unlocked. `Decisions.profileSeenWhenListing(kind, locked)` turns it into what the adapter needs (an unlocked private app looks like a work app; a locked one stays private so Niagara leaves it out). Pickers use the same rule (ticket 03 inlined it; it now delegates to `mayBeListed`). **Pinning an app's shortcuts is one of the long-press options**, so "may its app shortcuts be pinned" is answered by `profileForLongPressOptions` from ticket 01: private behaves like work. I did not add a separate `mayPinShortcuts`: it would be a constant `true` and its test would restate itself. Whether Android accepts a pinned shortcut from a private profile is not a decision the module makes; it is checked on the phone.
- **Three hooks, all essential.**
  - `SUGGESTION_ELIGIBILITY`: the only reader of the Private Space flag that takes one argument that is not the item and returns a boolean (`gqD7q….JtqOZV…`, 1638). It takes a usage record; the hook finds the one field of the record whose type is the item base class, at install time (it throws, so the module stays inactive, if there is not exactly one).
  - `OPTIONS_SHEET`: the only constructor that reads the flag (`VTeRaLtcXgU.<init>`). It asks the options builder (already hooked in ticket 01) and then checks the flag itself to offer "pin to the app list" for a private app's shortcuts. The builder hook restores the flag before the constructor reads it, so the constructor hook opens an `ItemFlags.Scope`: changes made inside it are undone when the constructor returns, last first.
  - `ADD_SHORTCUT_ITEMS`: see the next note.
- **The Add shortcut screen, a change of plan.** The ticket asked the finder to resolve "the Add shortcut screen check". That check cannot be wrapped (it sits in a coroutine loop; research notes). What can be changed is the items the loop looks at: `xN5Q…` is built only there, and its constructor is the only constructor of an item subclass that takes a `LauncherActivityInfo`. The finder anchors to the screen's coroutine, the one method that calls `LauncherApps.getShortcutConfigActivityList` (checked on the 1638 dexdump: one caller), and takes the constructor it invokes that builds an item subclass from a `LauncherActivityInfo`; that is one `findMethod` scan, and a future Niagara that gives another item class the same constructor shape would not be caught. An after-hook on the constructor makes an unlocked private app's items look like work apps for good (`ItemFlags.showForGoodAs`). **This is the one place the module changes a flag for good, which ADR 0001 rejects in general**; the ADR now records the exception and why. The justification is bytecode: in 1638 the constructor has a single caller, the coroutine of that screen. What the screen does with the items afterwards was not traced. Locked, the items stay private and Niagara leaves them out. **Unverified:** whether the screen then works for a private app's entries.
- **Locked-state handling uses `PrivateSpaceState`.** the locked state of the private profile (Android's `isQuietModeEnabled`), asked at the moment of the check; any failure counts as locked.
- **Not in this ticket: hiding rows that are already built.** Lifting the suggestions check puts private apps into the suggestions feed, and that feed is persisted: Niagara recomputes it at most every two hours (a day otherwise, `mSspcifkjw5Q3Aj`), so a suggested private app would stay on screen for hours after Private Space locks, and across a reboot. Spec story 32 ("stay hidden from suggestions while locked") therefore only holds once ticket 05's row filter is in, which covers every home page section: favorites, suggestions, and the media section a private music app would use (a leak the spec did not list). Until then the box "While locked: private apps aren't suggested" stays unchecked, and the device check says to repeat step 5 after ticket 05.
- **Unverified on the phone** (they stay unchecked): that locked private apps are not suggested; that Android accepts pinned shortcuts from a private profile; that the Add shortcut screen works for private entries.
- **Review round.** /code-review found: the exception to the ADR was not surfaced (fixed above), a test that duplicated the first long-press test (removed; see the decision note), the adapter finding the usage record's item field by reflection where the Finder never saw it (now `SUGGESTION_ITEM`, a field hook the fingerprint test covers), terms missing from the glossary (suggestions, app shortcut, long-press options, Add shortcut screen, listed), lines over 120 characters, a repeated lock check (`PrivateSpaceState.isLockedFor`), and some names (`showAs`, `Scope`). `profileSeenByPicker` now builds on `profileSeenWhenListing`.
- **Second review round.** Fixed: the Add shortcut anchor and its twenty-scan walk (above); `FlagChangeScope` held the global lock for the whole options sheet constructor even when nothing changed, which stalled background picker and suggestion work and widened the race window, so it now locks only when a flag is actually changed and releases when the scope closes, and every restore runs even if one throws; the `readers` lookup was outside the finder's guard.
