# 06: Tapping a locked private app unlocks it, then opens it

**What to build:** When the user triggers a private app while Private Space is locked, Android's unlock screen appears. Once the user unlocks, the app opens. This covers a **Niagara-button action** (tap or swipe up) and any other place Niagara still shows a locked private app, such as search. Cancelling the unlock opens nothing and changes nothing.

**Blocked by:** 03: Private apps in every app picker; 05: Hide locked private apps from favorites

**Status:** done-pending-device-check

- [x] **Decision module:** decides what a tap does (open now, or unlock first and open later), and handles pending launches. Unit tests cover:
  - a pending app opens once Private Space becomes available;
  - a cancelled unlock forgets the pending app;
  - a second tap replaces the pending app;
  - an unlocked private app opens directly.
- [x] **Unlock request:** Android's quiet-mode request for the private user, called directly.
- [ ] **Unlock request fallback:** Niagara's own unlock path. Not built, on purpose; see Notes.
- [x] **Opening after unlock:** the module itself opens the pending app when Private Space becomes available.
- [x] **Finder:** resolves Niagara's single app-launch method.
- [x] **Hook is essential:** it's added to the essential set.
- [ ] **On the phone:** with a private app set as the Niagara-button tap action and Private Space locked, tapping the button shows the unlock screen and then opens the app. Cancelling leaves the phone on the home screen.
- [x] **Device check:** steps added.

## Notes

- **Decision shape.** `PendingApp<App>` in the decision module is the state machine: `tap(app, kind, privateSpaceLocked, nowMillis)` answers `TapAction.OPEN_NOW` or `UNLOCK_FIRST` and keeps the **pending app**; `profileBecameAvailable(kind, nowMillis)` returns the app to open (once, and only for Private Space); `profileBecameUnavailable(kind)`, `unlockCancelled()`. Time is a parameter, so the class has no clock. `TapTest` has the four cases from the ticket and the edge cases (work profile availability ignored, locking again forgets, a tap that opens another app forgets, expiry). 
- **No signal for a cancelled unlock, so this part of the criterion is met only in the decision module.** No broadcast or callback is known that tells the requesting app that the user backed out of Android's credential screen; `unlockCancelled()` is called only when the unlock request itself fails (throws). So the pending app is forgotten by (a) a second tap replacing it, (b) any tap that opens something else, (c) Private Space locking again, (d) the unlock request failing (`unlockCancelled()`, called by the adapter), and (e) a timeout of 60 seconds (`PendingApp.TIMEOUT_MILLIS`), checked when the broadcast arrives rather than by a timer. 60 seconds is a judgement: long enough for a PIN or a fingerprint, short enough that a tap forgotten after cancelling does not open an app when the user unlocks Private Space some other way. The cost, written into the device check: cancel, then unlock within a minute through another route, and the app still opens.
- **Why the pending app expires lazily.** A timer would need a handler and a second code path in the adapter; comparing times when the broadcast arrives is the same behaviour with nothing to cancel.
- **Hooks.** `Hook.APP_LAUNCH` (the method that calls `LauncherApps.startMainActivity`, `AAqdJflv6N9m3Mj.ULNuaNwRhnIuhgDeV52bYgCY7E` on 1638), plus two field hooks the adapter needs to read the app's component without an obfuscated name: `LAUNCH_COMPONENT` (the one `ComponentName` field the launch method reads, in a small holder) and `LAUNCH_TARGET` (the field of the launch method's class that holds that holder). All three are essential. The user is not read from the item: an item that is private belongs to Private Space's profile, and the receiver passes the broadcast's user to `startMainActivity`.
- **Fingerprints checked on the 1638 dexdump**, by emulating `findAppLaunch` and `findLaunchTarget` over `dexdump -d` of `classes.dex` (a throwaway script, not DexKit, which has never run): one method calls `startMainActivity(ComponentName, UserHandle, Rect, Bundle)` (`AAqdJflv6N9m3Mj.ULNuaNwRhnIuhgDeV52bYgCY7E`); it reads exactly one `ComponentName` field (`XVYC3fHMxlmXmjh.S6IAQ…`); and exactly one field of `AAqdJflv6N9m3Mj` has that holder's type (`LymwWLwVTddmNDuus7mlek0`).
- **The unlock request is called directly** (`UserManager.requestQuietModeEnabled(false, privateUser)`, in `PrivateSpaceState.requestUnlock`), from the tap. AOSP lets Niagara do it while it is the foreground default launcher; for a profile that requires authentication it shows the credential screen and returns false. The return value is ignored: Private Space is unlocked when the profile-available broadcast arrives. **Unverified on LineageOS 24.**
- **Niagara's own unlock path is not built as a fallback.** In the 1638 bytecode `bhy75HKiWNVJcn4MG` is the only caller of `requestQuietModeEnabled`, so Niagara's path ends in the same framework call and cannot succeed where the direct call is refused; all it would add is Niagara's own error dialog, for a fourth fingerprint (`"open_action_item"`) and a launcher object. When the request throws (no Private Space profile, or Android refuses), the adapter forgets the pending app, logs a warning and lets Niagara's launch run as it always did, which for a locked private app is a silent no-op. If the lock query fails, the answer is "locked" (ticket 05's rule) and the tap asks for an unlock of a Private Space that is already unlocked; Android then answers at once, no `PROFILE_ACCESSIBLE` follows, and nothing opens until the minute passes or the user taps again. A transient failure of one `isQuietModeEnabled` call is the only way to get there, and it was accepted rather than designed around.
- **The receiver** is registered once (the flag resets if registering throws), with Niagara's application context and `RECEIVER_NOT_EXPORTED`, on the first tap that needs it (not at install: there is no Application yet in `onPackageReady`). Opening runs on the main thread (the default for a receiver) and every failure is logged instead of thrown, because an exception in a receiver would take Niagara down. A user that is not Private Space's counts as a work profile and cannot open or forget the pending app.
- **Which broadcast opens the app: `PROFILE_ACCESSIBLE`, not only `PROFILE_AVAILABLE` (a deviation from the run instructions, found in review).** `PROFILE_AVAILABLE` announces that quiet mode ended, which may precede the user's storage being unlocked; `startMainActivity` could then fail or be redirected, and the pending app would already be consumed. `Intent.ACTION_PROFILE_ACCESSIBLE` ("the profile's user is running and unlocked") exists in the SDK (`android.jar` of API 37) and is the moment apps can start. The module opens on `PROFILE_ACCESSIBLE`, and on `PROFILE_AVAILABLE` only if `UserManager.isUserUnlocked` already says so; `PROFILE_UNAVAILABLE` forgets the pending app. Which of the two Android actually delivers for Private Space is not verified; the device check covers it. The decision module's event is still "Private Space became available".
- **Unverified, written into `docs/device-check.md`:** that Android allows the request from a tap on LineageOS 24; that a receiver registered `RECEIVER_NOT_EXPORTED` gets the system's profile-available broadcast; that `startMainActivity` works the moment the broadcast arrives (Private Space's storage may not be unlocked yet; the check watches the log for that); and that the launch from the receiver is not blocked as a background start.
- **Search.** Niagara hides locked private apps from search itself (stock), so search offers no locked private app to tap; the hook still covers it if a later Niagara version shows one. The device check therefore uses the Niagara button.
- **Not replayed: Niagara's own bookkeeping.** For a locked private app the hook skips Niagara's launch method altogether, and the module starts the app itself afterwards, so Niagara's launch bookkeeping (usage counts, analytics) and the launch animation's source bounds do not happen for apps opened this way. The spec does not mention either.
- **Hole: the window while Private Space starts.** Android ends quiet mode first and unlocks the user's storage afterwards, so `isLocked()` is false for a short while and a tap then gets `OPEN_NOW`, forgets the pending app and runs Niagara's own launch against a user that is still starting. Treating that window as locked would change when ticket 05's rows reappear (Niagara rebuilds them on `PROFILE_AVAILABLE`, not `PROFILE_ACCESSIBLE`), so it was left. The device check records it.
- **The log tells the story.** The receiver and the tap write INFO lines (see the device check, step 10), because without them a failure of the receiver, a timeout and a blocked launch all look the same on the phone.

- **Known limits of the launch hook.** It sits on every app launch, so a personal app's launch also reads the item's flags and component: it reads the flags without the lock the flag-changing hooks use, so a launch of an item that a picker is filtering at that very moment could misread it (then the tap simply opens the app, as stock). A throwing hook falls back to Niagara's own method: `module.prop` sets `exceptionMode=protective` (ticket 01). The component is read only when a tap has to wait on it, so a personal or work launch touches no reflection beyond the flag reads.
