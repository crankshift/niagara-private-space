In this order. Nothing here has been done for you except the files and the key; no secret is set, nothing is pushed, no GitHub resource exists.

1. **Back up the release key in Bitwarden** (done, reported by the user on 2026-10-17). The folder `~/niagaraps-release-backup/` (mode 700, files 600) holds `niagaraps.jks` (the keystore: attach it), `NIAGARAPS_STORE_PASSWORD.txt` (the password, 32 bytes with no trailing newline; the key password is the same) and `NIAGARAPS_KEYSTORE_BASE64.txt` (the keystore as one line of base64, for the secret). Store alias `niagaraps`, type PKCS12, certificate SHA-256 `772745555dd5a6d9192e40a40801363a802b6e7f820583e4fd028d967867c622`. Tell the agent when it is saved. The release key is permanent: installed copies accept updates only from it, and with a new key users would have to uninstall the module before they could update it.
2. **Create the repo** `crankshift/niagara-private-space` on GitHub, public, empty (no README or licence: the repo has both).
3. **Push:** the local clone already has `origin` pointing at `git@github.com:crankshift/niagara-private-space.git`. Check `git branch --show-current` says `main`, then `git push -u origin main`. This is also ticket 10's "Push" criterion. It starts the `Build` workflow, which does not need any secret. (Ticket 10's step 2 edits the tested version; do that before this push if you have run the device check, so the pushed README is already right.)
4. **Set two secrets** on the repo:
   ```sh
   gh secret set NIAGARAPS_KEYSTORE_BASE64 -R crankshift/niagara-private-space < ~/niagaraps-release-backup/NIAGARAPS_KEYSTORE_BASE64.txt
   gh secret set NIAGARAPS_STORE_PASSWORD  -R crankshift/niagara-private-space < ~/niagaraps-release-backup/NIAGARAPS_STORE_PASSWORD.txt
   ```
5. **Submit the module, accept the invite and set the store repo's description:** these are ticket 10's steps 4 and 5; do them here. The dry run in step 7 checks `MODULES_REPO_TOKEN` against the store repo, which the submission creates, and the token's owner has push access to it only once the invite is accepted. (Whether the submission form wants the source repo pushed first is unknown; this order has it pushed.)
6. **Create `MODULES_REPO_TOKEN`:** GitHub > Settings > Developer settings > Personal access tokens (classic) > Generate new token (classic), only the `public_repo` scope, an expiry you will remember. Fine-grained tokens cannot reach an organization repo you only collaborate on. Set it (paste the token when asked): `gh secret set MODULES_REPO_TOKEN -R crankshift/niagara-private-space`.
7. **Run the dry run:** Actions > Release > Run workflow on `main` (or `gh workflow run release.yml -R crankshift/niagara-private-space`). It must pass every step except the two publish steps, which are skipped on a manual run. If "Check version, signature and changelog" fails, the log says which check refused. If "Check Modules Repo access" fails with "MODULES_REPO_TOKEN cannot push to …", the store repo does not exist yet, the invite is not accepted, or the token lacks `public_repo`. Running it before step 5 is harmless: the earlier steps still show whether they pass. Tell the agent the result.
8. **Delete the backup folder** once Bitwarden has the files and the secrets are set: `rm -rf ~/niagaraps-release-backup`. The working copy stays at `~/.android/keystores/niagaraps.jks`, and `~/.gradle/gradle.properties` has the four `NIAGARAPS_*` lines.
