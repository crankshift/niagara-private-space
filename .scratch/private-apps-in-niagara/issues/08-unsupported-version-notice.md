# 08: Unsupported-version notice

**What to build:** When the module can't activate on a Niagara version, the user sees one dismissable home-screen tip, in Niagara's own tip style: "Niagara Private Space doesn't support Niagara <version> yet". It appears at most once per Niagara version. If Niagara's tip system can't be found either, a short Toast shows instead. Vector's log always gets a line.

**Blocked by:** 01: Add a private app to favorites from its long-press menu

**Status:** done-pending-device-check

- [x] **Decision module:** decides whether the notice is due from the current Niagara versionCode and the last one notified. Unit-tested: shown once per version, shown again for a new version, never shown when the module activated.
- [x] **Tip:**
  - It's registered with Niagara's tip manager under the borrowed `XIAOMI_FULL_SCREEN_GESTURES_MIUI_12` type.
  - The provider and its dismiss and click callbacks are dynamic proxies dispatched by return type.
  - The message is free text, and the button and icon resources are resolved at runtime.
- [x] **Fallback:** a Toast from Niagara's application context when the tip manager or factory can't be found.
- [x] **Storage:** the last-notified versionCode lives in a module-owned preferences file inside Niagara's data, never in Niagara's own keys.
- [ ] **On the phone:** a forced-unsupported debug path shows the tip, which can be dismissed and doesn't come back after restarting Niagara. Forcing the tip system missing shows the Toast.
- [x] **Device check:** steps added.

## Notes

- **Decision shape.** `Activation.notify` is true when the module could not activate. `Decisions.noticeDue(activation, versionCode, lastNotifiedVersionCode)` is `notify` and a version not already told; `Decisions.noticeChannel(activation)` is a tip when the tip system is available and a Toast otherwise; `Decisions.noticeText(versionName)` is the spec's sentence. `NoticeTest` covers the ticket's three cases (once per version, again for a new version, never when active) and the rest. A version that is greater than the last one told about counts as new, and so does a smaller one (a downgrade).
- **The tip system is the second optional part, `OptionalPart.TIP_SYSTEM`.** Six hooks: the tip manager's constructor, its registration method, the factory that builds a tip, two fields of the manager (the home page it tells, a paused flag) and the home page's field that holds the factory. One missing makes the notice a Toast, not the module inactive. **A change to ticket 07's rule:** a part's availability no longer depends on the module being active, because the notice needs the tip system exactly when the module is inactive; `ActivationTest` says so.
- **The notice also covers two failures the ticket did not name.** When the finder cannot run at all, and when the hooks cannot be installed after all (`Activation.afterFailedInstall`: nothing of the module is in Niagara, the tip system stays available), the user hears the same notice, as a Toast when the finder did not run. Both end with the module inactive, which is the case the ticket describes.
- **Fingerprints checked on the 1638 dexdump** (a throwaway script emulating `findTipSystem`, not DexKit): one class holds `"Thsi{tt="`; one static method of 9 parameters returns it with the factory first, a `CharSequence` fourth, an `int` last, and interfaces at the 7th and 8th places; the tip class has one constructor, and exactly one of its parameter types (`kRCKGSQBLvaaeh63O`) has a void method taking an enum and an interface; that enum's static initialiser holds the string `XIAOMI_FULL_SCREEN_GESTURES_MIUI_12`; the manager has one constructor, one boolean field and one other non-`java.` field (the home page), and the home page class has exactly one field of the factory's type.
- **A correction to the research.** The research said the tip types' names survive; they survive only as strings (each constant's name), not as field names. So the type is looked up with `Enum.valueOf(type, "XIAOMI_FULL_SCREEN_GESTURES_MIUI_12")` and the finder checks that the string is in the enum. Recorded in the research notes.
- **Crash safety, the main risk of this ticket.** A provider that cannot build its tip makes the home page throw. So the module registers the tip only once the home page is up and not paused, polling every half second for a minute from the main thread after the manager is created, so that Niagara builds the tip inside the module's try block. If that fails, the tip is taken back (the provider says no and the manager is asked again) and a Toast is shown. Later builds (the home page pausing and resuming) call the same code that already worked once. This is not seen running.
- **The version told about is written (synchronously) after the tip's pieces are built and before it is registered**, so a crash at that moment costs at most a notice that is never shown for that version, and never shows it twice. If building the pieces fails (a missing resource, a renamed tip type), nothing is marked yet and the Toast takes over. An earlier version of this code marked first and then built, which would have shown nothing in that case (found in review).
- **Storage** is `niagara_private_space.xml` in Niagara's own `shared_prefs`, written through Niagara's context; the key is `last_notified_niagara_version_code`. Niagara's keys are never read or written.
- **The debug path.** `DebugSwitches` reads the system properties `debug.niagaraps.unsupported` and `debug.niagaraps.no_tip_system` once at start, through reflection on `android.os.SystemProperties` (hidden API; unknown whether Niagara's process may read them, and the device check says what to do if not). They are off unless set to `1`, and they remove one essential hook (`APP_LAUNCH`) and one tip hook (`TIP_MANAGER`) from the report before the decision module sees it. The once-per-version rule applies to a forced notice too: the device check deletes the preferences file to repeat.
- **Unverified on the phone** (criterion left unchecked): everything the tip does inside Niagara. In particular that mask 210 gives the intended text, button and icon; that the dismiss callback's `Boolean.TRUE` is what Niagara expects (read from the tip class); that Android lets Niagara's process read `debug.*` properties; that `Application` exists when the Toast runs.
- **Known costs, from the research.** The tip's dismiss and click send a consent-gated analytics event keyed with the borrowed type's name. And the manager matches tips by type only, so a real owner of the Xiaomi type would remove ours; on a Xiaomi phone the notice could be removed by Niagara's own code. Neither was addressed.
- **Review round 1.** /code-review found, and this commit fixes: the mark-before-build ordering above; the factory found by scanning the holder's fields for a value of its class (now the home page's typed field, a hook the finder resolves, `TIP_FACTORY_INSTANCE`); `apply()` instead of `commit()` behind a "written before" claim; claims about Niagara and Android stated as fact (softened, and "home-screen" replaced by the glossary's "home page"); `NoticeTest` repeating the hook list (a shared `HookGroups` fixture now names every hook once, and `ActivationTest` checks the groups cover `Hook.entries`); `DebugSwitches` wording and a vague name; a stale README; a `final` variable name; spec bullet nesting; glossary terms (Tip, Tip system, Notice, Debug switch). Declined: moving the Toast-on-failure policy and the `!dismissed` answer into the decision module (they are adapter error handling and Niagara protocol); a unit test for `DebugSwitches.apply` (two list removals; the device check exercises it); splitting `Notice` (it is one flow). Accepted as written: a version that cannot be read counts as version 0 and is told once.
- **Spec review round 1.** Found, and fixed here: the Toast fallback after a failure while building the tip's pieces (the ordering bug above); the posted Toast runnable and the tip's failure path were not guarded and could throw on the main looper (both are now guarded and log); the stale "Expected log line" (the tip system's pieces and the `without TIP_SYSTEM` clause are described) and a wrong "needs root" for the debug properties (they are usually settable from the adb shell; the steps use root, which works either way). **A deviation from the ticket's words, kept:** "the provider and its dismiss and click callbacks are dynamic proxies dispatched by return type" holds for the provider only. The two callbacks are single-method interfaces whose methods both return `Object`, so the proxies answer any method that is not `Object`'s and take their meaning from which interface they implement (the factory's 7th and 8th parameters), never from a method name. **Still unguarded, as admitted above:** later builds of the tip, when the home page pauses and resumes, run in Niagara's own code and repeat the build that already worked once. Accepted: a DexKit that cannot load gives the same notice as an unrecognised Niagara, and the tip manager's constructor hook is installed on every start of an unsupported version, even when the notice is not due, because the preferences cannot be read before the Application exists.
